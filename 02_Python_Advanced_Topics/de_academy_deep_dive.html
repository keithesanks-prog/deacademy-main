1. AWS Lambda & Python Integration

What does the lambda_handler(event, context) actually do?
The lambda_handler is the entry point. Think of it as the Main Office.
  • event: A dictionary containing data about what triggered the Lambda (e.g., S3 bucket name, file key, or an API request).
  • context: Information about the runtime environment (how much time is left before timeout, log group name, etc.).
In our project, when a CSV drops into S3, AWS sends that metadata inside the event object, telling Python exactly where to find the data.
Why do we use Python for Lambda instead of just SQL?
Python acts as the Traffic Controller. SQL is great at manipulating data inside a database, but Python is needed to:
  1. Communicate with APIs (pulling data).
  2. Handle files in S3 (renaming, moving, checking existence).
  3. Trigger specific Snowflake commands based on logic (e.g., "If file size > 1GB, use a larger warehouse").

Think of Python/Lambda as the Delivery Truck driver who knows the route and carries the manifest (Event). Snowflake/SQL is the Warehouse worker who organizes the boxes once the truck arrives.

What are the most common Python libraries used in Data Engineering?
  • boto3: The AWS SDK for Python. Used to talk to S3, Lambda, Secrets Manager, etc.
  • pandas: For small-to-medium data manipulation (though often avoided for massive datasets in favor of SQL).
  • json: Crucial for parsing API responses and the event object.
  • snowflake-connector-python: To execute SQL commands from Python.

2. DBT: Jinja SQL & Hooks

Is DBT just "Advanced SQL"?
Not quite. DBT uses Jinja SQL. Jinja is a templating language (originally for Python web frameworks) that allows you to add logic to your SQL.

It takes a .sql file, processes the Jinja blocks (the parts in {{ }} or {% %}), and "compiles" it into raw ANSI SQL that Snowflake understands.
What do {{ ref() }} and {{ source() }} actually do?
They are Dependency Managers.
  • {{ source('raw_data', 'sales') }}: Points to raw data defined in your sources.yml.
  • {{ ref('stg_sales') }}: Points to another model within DBT.
Why use them? Instead of hardcoding FROM MY_DB.PUBLIC.SALES, you use refs. This allows DBT to build a Lineage Graph (DAG) and know exactly which table needs to be built first.
What are Pre-Hooks and Post-Hooks?
They are Event Listeners for your model.
  • Pre-Hook: Runs before your main SELECT statement. Often used for clearing temp tables, granting permissions, or triggering data loads.
  • Post-Hook: Runs after your model finishes. Used for logging, vacuuming, or sending notifications.
-- Example of a Pre-Hook in a model's config block {{ config( materialized='incremental', pre_hook="DELETE FROM {{ this }} WHERE load_date = current_date" ) }} SELECT * FROM {{ ref('stg_data') }}

Think of Hooks like the "Set up" and "Clean up" crews at a concert. The Pre-hook sets the stage (instruments, lights). The SQL Model is the band playing. The Post-hook cleans up the stage after the show.

What is a Macro in DBT?
A Macro is a Reusable Snippet of code (like a Python function). If you find yourself writing the same complex CASE statement or JOIN logic in 10 different models, you write it once in a Macro and call it like this: {{ my_cool_macro(column_name) }}.

3. Snowflake Stages & Data Loading

What is a Snowflake Stage?
A Stage is a Landing Zone. It is a pointer to a location where data files are stored before they are loaded into a table.
  • Internal Stage: Data is stored inside Snowflake's own file storage.
  • External Stage: Data is stored in your own cloud storage (S3, GCP Bucket, Azure Container).
What does FROM @my_stage mean?
The @ symbol indicates a Stage Reference.

When you run SELECT $1, $2 FROM @ext_stage/sales_data.csv, Snowflake isn't looking for a table. It is reading the raw file directly from the stage as if it were a table, where $1 is the first column in the file.
What is the COPY INTO command?
This is the Bulk Loader. It is the most efficient way to move large volumes of data from a stage into a permanent Snowflake table.
-- Loading JSON data from a stage into a table COPY INTO RAW_SALES_JSON FROM @S3_STAGING_ZONE/daily_uploads/ FILE_FORMAT = (TYPE = 'JSON');

Think of an External Stage as a "Reserved Parking Spot" at the airport. Snowflake knows exactly where it is and has the key (Credentials) to open your trunk (S3 Bucket) to get the luggage (Data).

Why use a Stage instead of just uploading files directly?
Stages allow for Scalability and Automation. Instead of manually uploading a file to a table, you tell Snowflake: "Watch this stage. Every time a new file arrives via the Lambda Traffic Controller, use the COPY INTO Bulk Loader to ingest it."

4. DBT Build: The Master Execution Flow

What is dbt build and why should I use it?
dbt build is the "One Command to Rule Them All". Instead of running dbt seed, then dbt run, then dbt test, dbt build does everything in a single, perfectly ordered pass.

If a test fails for a specific model, DBT is smart enough to stop and not run the downstream models that depend on that broken data.
In what order does dbt build process everything?
When you trigger a build, DBT follows a strict sequence to ensure data integrity:
  1. on-run-start hooks: Global setup scripts (e.g., creating schemas).
  2. Seed files: Loading small CSVs and testing them immediately.
  3. Source freshness checks: Ensuring your raw data isn't stale.
  4. Snapshots: Capturing historical changes if configured.
  5. Models: Running transformations (ordered by dependency).
  6. Tests: Validating the output of your models.
  7. on-run-end hooks: Final clean-up or logging scripts.

Think of dbt build as an Automated Assembly Line. If the engine test fails at Station 6, the line stops before it tries to put the car body on at Station 7. It prevents a "broken car" from ever reaching the dealership (your production dashboard).

Pro Tip: Stick to dbt build for your production pipelines. It ensures that bad data never propagates downstream by stopping the flow exactly where the error occurs.
